## Findings considered and rejected

- **Substring-scan in `get_all_matching_prices` (`services/price_lookup.py:234`)**:
  not worth doing now — it is an O(n) scan of a per-client in-memory dict, but
  catalogs are small and there is no evidence of a performance problem. Revisit
  only if large catalogs appear.
- **Webhook payload signing / replay protection (`api/webhook.py:20`)**: the
  static `DIVAR_IDENTIFICATION_KEY` equality check (already constant-time via
  `hmac.compare_digest`) is the documented Divar platform convention; not a
  defect. Revisit only if Divar introduces payload signatures.
- **Webhook idempotency via `messages.divar_message_id`**: the duplicate-reply-on-
  redelivery behavior is a **documented, deliberate tradeoff** in `plans/PHASE2.md`
  §2.1 ("the reply is idempotent in effect ... this design deliberately avoids"
  persisting per-conversation/per-message markers). Not converted to a fix plan to
  avoid contradicting a dated design decision. The only open thread is *decision
  drift*: the `messages` table + unique `divar_message_id` column are built but
  unused (dead scaffolding for a future phase) — raise with the maintainer as a
  design question, not an implementation task.
